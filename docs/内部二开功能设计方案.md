# 新博 IM 内部二开功能设计方案

**日期**：2026-11-18　｜　**阶段**：项目设计（不含代码）　｜　**目标**：把 OpenIM 从 IM 工具扩展为公司内部「沟通 + 人事管理」一体化平台

---

## 一、设计原则（先定调子）

1. **不侵入 OpenIM 核心**：聊天、通讯录、音视频保持原样。所有新功能做成独立的 `oa` 服务，出问题不影响主业务。
2. **用户体系统一**：OA 数据全部用 IM 的 `userID` 关联，员工在 IM 里就是一个人，不搞两套账号。
3. **数据隔离**：OA 数据存 MongoDB 独立集合（`oa_` 前缀），不动 `user/attribute/account` 这些核心集合，方便日后单独备份、迁移、升级 OpenIM。
4. **复用现有基建**：文件（打卡照片、报告附件）存 MinIO 的 `oa` 桶，缓存用 Redis，网关走现有 Nginx 同源反代。
5. **权限最小化**：普通员工看不到别人的数据；管理层只看自己部门；公司管理员看本公司；总部超管看全集团。
6. **多分公司（多租户）**：一套实例承载多家公司，所有业务数据带 `company_id`，分公司之间互不可见。**新功能从第一天就要按多租户设计**，不能等以后再补（详见第五章）。

### 2.4 会议功能 · 详细设计（线上会议 + 实体会议室）

**先分清两件事，别混为一谈**：

| | 线上会议（视频会议） | 实体会议室预订 |
|---|---|---|
| 资源性质 | 虚拟的，无限量，可随时创建 | 真实稀缺资源，同一时段只能一组人用 |
| 发起方式 | **管理层一键发起 → 员工点链接进来** | 员工/管理层查询空闲后预订 |
| 需要防冲突吗 | 不需要，一个会议一个房间互不干扰 | 需要，两人抢同一时段会撞车 |
| 需要签到/违约吗 | 不需要，进来就进来 | 需要，防止订了不去浪费房间 |
| 优先级 | **必做**（现有 LiveKit 已支持） | **可选**，看公司有没有实体房间 |

> 结论：你说的「管理层发起、员工进来参加」是**线上会议**的正确形态，本来就该极简——无需预约、无需冲突检测、无需违约机制。之前详细的那套是针对**实体会议室**的，只有公司确实有需要排期的实体房间时才做；没有实体房间，整个 F18 可以直接砍掉。

#### 2.4.1 线上会议（必做，方案已现成）

管理层在 IM 里点「发起会议」→ 系统调 LiveKit 建一个临时房间 → 生成链接通过 IM 推给参会人 → 员工点击加入 → 音视频通话（这套 LiveKit 已部署并验证过 token 签发）。管理层可控制谁能发起、会前提醒、会议时长。这块**不产生新的复杂设计**，复用现有能力即可。

#### 2.4.2 实体会议室预订（可选分支，有实体房间才做）

下面这套只针对实体房间：

**会议室资源** `oa_meeting_room`：`room_id`、名称、楼层/位置、容纳人数、设备标签（投影/视频会议/白板）、开放时段、是否需要审批、状态（可用/停用）。

**预订记录** `oa_meeting_booking`：`room_id`、预约人 `user_id`、开始/结束时间、主题、参会人列表、状态（已预约/已签到/已取消/已过期/违约）、签到时间、关联的视频会议房间号（复用现有 LiveKit）。

**五步闭环**（见流程图）：

1. **发起预约**：选会议室、时段、参会人、主题。系统先查该时段是否空闲。
2. **冲突检测**：这是核心难点。两个人同时抢同一时段，前端校验会漏。必须在 `oa_meeting_booking` 上建 `(room_id, start_time, end_time)` 的**唯一约束或事务锁**，以数据库为最终仲裁——后提交的人直接收到「该时段已被占用」，而不是两人成功后再人工协调。
3. **审批锁定**：需要审批的会议室走管理层审批；通过后写入数据库正式占位，并发起 IM 通知参会人。
4. **会前提醒 + 签到**：会前 10 分钟 IM 推送提醒；参会人到会议室扫码（或点签到）确认使用。
5. **签到或释放**：签到正常；**超时 15 分钟未签到自动释放资源**，并记录一次违约。累计违约 N 次（管理层可配）限制其预订权限——这是防止占而不用的关键。

**和 IM 的联动（这是比独立会议室系统更值钱的地方）**：

- 预订成功自动建一个群聊/发送邀请，参会人一键进群；
- 房间如有视频设备，预订时可挂一个线上会议链接，到点一键发起（线上会议本身无需预订，见 2.4.1）；
- 会前提醒、审批结果、违约通知全走 IM 系统消息，员工不用记另一个 App；
- 会议纪要可存到知识库（F19），和会议记录关联。

**管理层配置项**：是否需要审批、可预约时长上限、提前多久可订、违约几次冻结权限、超时释放分钟数——和 F8 打卡一样做成可配置。

**为什么必须做这两件事（根因说明）**：

- **防冲突的根源**：「查询空闲」和「提交预订」是两次独立请求，中间存在时间窗口。A 查完到提交之间，B 也查到空闲，两人都以为订到了。前端校验只存在于各自浏览器，互相看不见，必然撞车。数据库是两人唯一共享的地方，所以冲突仲裁必须放在那里（唯一约束/事务锁），后提交者收到「已被占用」。
- **防占而不用的根源**：会议室是公司的稀缺公共资源。如果预订零成本、无追责，就会出现「随手订 / 订多个备选 / 会议取消也不释放」，导致房间空着却被占、真正需要的人订不到，最终大家放弃系统改回线下抢——典型的公地悲剧。签到 + 超时释放 + 违约计次，本质是给占用资源的行为加上成本，让资源真正流转起来。

这两点不是过度设计，是不做就一定会发生、且会让系统失效的问题。

**我的建议**：
- **线上会议**——不用等二期，现有 LiveKit 已具备能力，补一个「管理层发起 + IM 推链接」的入口即可，成本很低。
- **实体会议室预订**——放**二期**，和审批中心（F13）一起做（审批流共用）。而且**前提是公司确实有需要排期的实体房间**；如果办公区没有固定会议室或不需要预约，这项直接砍掉，不要为自己用不上的功能付出维护成本。

## 三、核心功能详细设计

### F4/F5 员工岗位标识 + 组织架构

**设计要点**：不在 IM 原生的 `attribute` 集合上加字段（那是核心表），新建 `oa_employee` 集合，用 `user_id` 一对一关联。

员工档案字段：

| 字段 | 说明 |
|---|---|
| `user_id` | 关联 IM 用户，主键 |
| `real_name` | 真实姓名（IM 昵称可能是花名） |
| `department_id` | 所属部门，指向 `oa_department` |
| `position` | 岗位名称，如「后端工程师」 |
| `responsibilities` | 负责工作描述，管理层可见的核心字段 |
| `job_title` | 职级，如 P6 / 主管 |
| `manager_id` | 直属上级 `user_id`，决定审批链和可见范围 |
| `entry_date` | 入职日期 |
| `status` | 在职 / 离职 |

**管理层查看方式**：组织架构树（部门 → 员工卡片），点开员工显示 `position` + `responsibilities`；另提供「岗位职责一览」表格，支持按部门筛选、导出。

**与建号流程打通**：现在注册入口已关，员工由管理员创建。建号时同步写入 `oa_employee`，一步完成「建账号 + 录岗位」，避免两处维护。

### F1 员工拍照打卡

**流程**：员工点打卡 → 前端调起摄像头拍照 + 获取 GPS → 上传照片到 MinIO → 提交打卡记录 → 服务端判定正常/迟到/早退 → 回写结果。

打卡记录 `oa_checkin` 字段：

| 字段 | 说明 |
|---|---|
| `user_id` / `date` | 谁、哪天 |
| `type` | 上班卡 / 下班卡 |
| `checkin_time` | 服务端时间（**不信任客户端时间**） |
| `photo_url` | MinIO 照片地址 |
| `location` | 经纬度 + 地点名（可选，按规则） |
| `device_info` | 设备型号 + IP，辅助防代打 |
| `status` | 正常 / 迟到 / 早退 / 待补卡 |

**防代打三件套**：服务端时间戳、GPS 围栏（在规则里配公司坐标和半径）、照片带水印（时间+姓名+定位绘制到图片上）。注意：真正的人脸识别成本高，一期不做，靠「拍照 + 围栏 + 水印」已能覆盖内部管理场景。

**关键约束**：浏览器非 HTTPS 环境拿不到摄像头和定位权限。打卡入口必须走 HTTPS（现有隧道已是 HTTPS，正式部署要配证书）。PC 端建议只读，打卡主战场放手机端。

### F2 工作报告管理

**报告类型**：日报、周报、月报，可配模板（今日完成 / 明日计划 / 遇到问题）。

报告 `oa_report` 字段：`user_id` / `type` / `period`（归属日期或周次）/ `content` / `attachments` / `status`（草稿、已提交、已点评）/ `reviewer_id` / `review_comment` / `review_time`。

**流转**（遵循 3.1 统一规范）：员工提交 → 系统按 `manager_id` 自动指派组长 → IM 推送「你有 1 份待点评日报」→ 组长点评并勾选上报 → 领导查阅点评后归档 → 员工收到结果提醒。组长筛掉不必上报的日报，领导只看上报的那部分。

**统计**：按部门统计提交率（已提交人数 / 应提交人数），未交名单可一键催交（触发 F10 的 IM 消息）。

### F3 出勤记录管理

**数据来源**：`oa_checkin` + `oa_leave`（请假）+ `oa_makeup`（补卡）三张表汇总。

**输出**：月度考勤表，每人一行，列出出勤天数、迟到次数、早退次数、请假天数、补卡次数、异常标记。支持按部门/月份筛选、Excel 导出。

**职责划分**（遵循 3.1 统一规范）：员工看自己的；组长看直属下属的考勤明细并处理异常；领导看本团队考勤汇总（组长处理后的结果）；HR/管理员看全公司并可修正（修正必须写审计日志 F12）。

### F6/F7/F8 请假、补卡与规则

- **请假**（遵循 3.1 统一规范）：类型（事假/病假/年假/出差）、起止时间、事由 → 员工发起 → 组长审批（按 `manager_id`）→ 通过后自动标记对应日期为「请假」并上报领导知悉，出勤统计直接采信；驳回则退回员工。
- **补卡**（遵循 3.1 统一规范）：选日期 + 时间 + 原因 → 员工发起 → 组长审批 → 通过后写入一条 `source=makeup` 的打卡记录并上报领导，审批结果进考勤汇总。
- **考勤规则** `oa_attendance_rule`：按部门或全局配置——上班/下班时间、迟到宽限分钟、GPS 围栏坐标与半径、节假日表、是否强制拍照、是否允许补卡。

### F8 补充：打卡完全由管理层自由配置

需求确认：**什么时候打卡、谁需要打卡、怎么打卡，全部由管理层在后台配置，不写死。** 这样公司改作息、换班次、临时调整都不用改代码。

配置项设计（管理层在后台可视化配置，实时生效）：

| 配置项 | 可选内容 | 说明 |
|---|---|---|
| 功能总开关 | 启用 / 停用 | 一键关闭全公司打卡，不改代码 |
| 打卡时间窗口 | 上班卡/下班卡各自的起止时间 | 例如上班卡 07:00–09:30，窗口外打卡记异常 |
| 适用人群 | 全公司 / 指定部门 / 指定岗位 / 指定个人 | 可对不同人群配不同策略，如外勤只拍照不定位 |
| 打卡方式 | 拍照 / GPS 定位 / WiFi 校验 / 任意组合 | 勾选启用哪些，管理层自由搭配 |
| 工作日设置 | 周一至周五 / 大小周 / 自定义 | 配合法定节假日表 |
| 判定规则 | 迟到宽限分钟、早退判定、补卡是否允许及次数上限 | 例如宽限 10 分钟内不算迟到 |

**策略优先级**：个人 > 部门 > 全局。管理层可建多套策略挂给不同部门，某员工没单独配就继承部门策略，部门也没有就用全局默认。这样既灵活又不繁琐。

**实时生效**：策略改动写入 `oa_attendance_rule` 后即时生效，员工端下次打卡按新规则判定；已产生的历史打卡记录不受影响（打卡时把生效的策略快照 ID 一并存入 `oa_checkin`，保证历史可追溯）。

### 3.1 统一流转规范：员工提交 → 组长操作 → 领导查看归档

**这是所有"员工情况类"功能（日报、请假、补卡、考勤异常）的共同骨架，不再各自为政。** 三级角色、两级流转：

| 角色 | 定位 | 动作 |
|---|---|---|
| 员工 | 产生情况 | 提交日报 / 发起请假补卡 / 每日自动产生打卡记录 |
| 组长（直属上级 `manager_id`） | **操作层** | 点评日报、审批请假补卡、处理本组考勤异常；决定哪些上报领导 |
| 领导（上级的上级，或按汇报链指定） | **查看归档层** | 只看组长上报的内容，做最终点评/归档/决策，不淹没在全部明细里 |

**设计意图**：组长是第一道闸门，替领导过滤掉不必看的日常明细；领导只看经过组长处理的结果。这样既保证领导掌握团队情况，又不让其被每个人的打卡、每份日报淹没。

**三类功能都套这条链，但"组长操作"的具体动作不同**：

| 类型 | 员工端产生 | 组长操作 | 领导可见 |
|---|---|---|---|
| 日报（F2） | 提交日报 | 点评 + 勾选上报领导 | 组长上报的日报；领导点评后归档 |
| 请假 / 补卡（F6/F7） | 发起申请 | 审批通过 / 驳回；通过后自动写入考勤 | 审批结果 + 团队考勤汇总 |
| 打卡异常（F1/F3） | 每天自动生成打卡记录 | 不逐条审，只处理异常（迟到 / 漏卡 / 地点异常 / 补卡） | 团队考勤汇总与异常统计 |

**状态机统一**：所有情况类数据都要经历 `员工提交 → 待组长处理 → （组长处理后）待领导查阅 → 已归档` 四个阶段，用统一的状态字段与推送逻辑，便于复用审批引擎与待办中心。

**权限落地**：可见范围严格按 `oa_employee.manager_id`（直属上级）和汇报链计算——组长只看直属下属，领导看本团队（含下属组长的人），跨部门/跨分公司一律不可见。**前端过滤仅用于演示，真实的身份与范围必须由服务端从登录态的 `userID` + `company_id` 解析后强制注入查询，前端一律不传、不信客户端声明的身份。**

## 四、权限矩阵

| 功能 | 普通员工 | 组长（直属上级） | 领导（上级的上级） | HR/管理员 |
|---|---|---|---|---|
| 自己打卡 / 提交报告 | ✅ | ✅ | ✅ | ✅ |
| 查看自己考勤 / 报告 | ✅ | ✅ | ✅ | ✅ |
| 查看下属考勤 / 报告明细 | ❌ | ✅（直属下属） | ❌（只看汇总） | ✅（全公司） |
| 查看本团队考勤汇总 / 已上报报告 | ❌ | ✅ | ✅（组长上报的） | ✅（全公司） |
| 点评日报 / 勾选上报领导 | ❌ | ✅ | ❌（只点评上报的） | ✅ |
| 审批请假 / 补卡、处理考勤异常 | ❌ | ✅ | ❌（看结果） | ✅ |
| 归档 / 最终决策 | ❌ | ❌ | ✅ | ✅ |
| 维护员工岗位信息 | ❌ | ❌ | ❌ | ✅ |
| 配置考勤规则 | ❌ | ❌ | ❌ | ✅ |
| 修正考勤数据 | ❌ | ❌ | ❌ | ✅（留审计） |

**说明**：组长是操作层（看明细、审批、点评、上报），领导是查看归档层（只看组长上报的汇总与结果、做最终归档），二者职责不重叠，避免领导被日常明细淹没。

权限判定统一走 `oa_employee.manager_id` 和 `department_id`（领导范围按汇报链向上取两级），不新增独立角色表——复用 IM 现有的 admin 体系做全局管理员即可。

## 五、多分公司（多租户）设计

**已确认的三个决策**：① 分公司之间**互不可见**；② **一套实例共享**，靠 `company_id` 逻辑隔离；③ 员工**一人只属一家公司**。

这三条定下来，方案就明确了：**共享一套 OpenIM + 一套 OA 服务，所有数据按公司打标隔离**。好处是只维护一套、总部能直接看全集团数据；代价是隔离必须靠代码纪律，不能依赖任何"默认不可见"。

### 5.1 数据模型调整

新增 `oa_company`：`company_id`、公司简称/全称、统一社会信用代码（可选）、状态、创建时间。

**所有 OA 集合统一增加 `company_id` 字段**，并作为**联合索引的第一列**：

| 集合 | 索引建议 |
|---|---|
| `oa_employee` | `(company_id, user_id)` 唯一 |
| `oa_department` | `(company_id, parent_id)` |
| `oa_checkin` | `(company_id, date, user_id)` |
| `oa_report` | `(company_id, period, user_id)` |
| `oa_attendance_rule` | `(company_id, scope)` |
| `oa_meeting_room` | `(company_id, room_id)` |
| `oa_meeting_booking` | `(company_id, room_id, start_time)` |

> **铁律**：`company_id` 必须从第一天就加，哪怕现在只有一家公司。后期补这个字段要改所有表、所有查询、所有接口，还要回填历史数据，成本是现在的几十倍。

### 5.2 隔离怎么做（关键在"不能漏"）

隔离不是加个字段就完事，要堵住所有跨公司入口：

1. **DAO 层强制注入**：所有查询由统一的数据访问层拼接 `company_id`，业务代码不写裸查询。用中间件从登录态取出 `company_id` 注入 context，禁止手工传参。
2. **通讯录隔离**：OpenIM 原生通讯录是全实例可见的，必须改。前端通讯录页不再调 OpenIM 的全局用户接口，改走 OA 的 `/oa/contacts`（只返回本公司员工）；全局搜索同样要过滤。
3. **跨公司加好友/建群要拦**：这是最容易漏的地方。A 公司的人如果知道 B 公司某人的 `userID`，通过接口可能直接加好友发消息。解决办法有两个：一是在 OA 侧校验（简单，但绕过 OA 直连 IM 接口就失效），二是在 chat 服务的 `msg/send_msg`、`friend/add` 等入口加公司校验中间件（侵入小、覆盖全）。**建议用第二种**，因为它是唯一能兜住"知道 ID 就能绕过前端"的层次。
4. **权限分级**：总部超管（跨公司）→ 公司管理员（本公司）→ 部门主管（本部门）→ 员工（本人）。原有 `chatAdmin` 保留为总部超管，新增 `oa_employee.role` 区分后两级。
5. **登录时确定公司**：用户登录后由 OA 返回其 `company_id`，前端全程带着走，不做"切换公司"（因为一人只属一家）。

### 5.3 多分公司会带来的具体问题

| 问题 | 建议处理 |
|---|---|
| 员工从 A 公司调到 B 公司 | 不做物理迁移。`oa_employee` 增加变更记录表，原公司数据保留在原 `company_id` 下，新公司重新建档，历史可查但归属清晰 |
| 同一手机号在两家公司 | 一人只属一家时一般不会出现。建号接口仍要校验全局唯一并给出明确提示，避免管理员困惑 |
| 各分公司作息不同 | 考勤规则按 `company_id + 部门` 配置，互不影响 |
| 总部要看全集团数据 | 总部超管的查询跳过 `company_id` 过滤，或显式传 `company_id=ALL`，该能力只对超管开放 |
| 分公司退出 | 支持按 `company_id` 整体导出、整体删除，不牵连其他公司 |
| 成本分摊 | 统计存储量与消息量时按 `company_id` 分组，为日后核算留出数据 |

### 5.4 不建议做的事

**不要改 OpenIM 核心表做多租户。** 它的 `user`/`group` 表本身没有公司概念，硬加字段会导致升级冲突、后续版本无法合并。组织关系（谁属于哪家公司、什么岗位、什么部门）全部放 OA 层维护，IM 层只通过群组和接口校验实现隔离。这样即使某天某分公司要独立部署，也只是迁 OA 数据，IM 不受影响。

## 六、技术方案要点

- **服务形态**：新增 `oa-api`（HTTP，对联前端）+ `oa-rpc`（gRPC，可选）；一期规模小可以只做单服务 `oa-api`，直接连 MongoDB。
- **目录位置**：新建 `src/xinbo-oa/`（与 `src/open-im-server`、`src/chat` 平级），独立 go.mod 或复用现有，建议独立便于升级。
- **网关**：Nginx 加 `location ^~ /oa/` 反代到 oa 服务，前端全部用同源相对路径，沿用现有隧道/HTTPS 方案。
- **鉴权**：前端调 `/oa/*` 时带上 IM 的 chatToken，OA 服务用与 chat 相同的 JWT secret 校验，从中取 `userID`。不另发登录态。
- **数据集合**：`oa_employee`、`oa_department`、`oa_checkin`、`oa_report`、`oa_leave`、`oa_makeup`、`oa_attendance_rule`、`oa_audit_log`，全部在 `openim_v3` 库内，与核心集合物理隔离。
- **文件存储**：MinIO 新建 `oa` 桶，路径按 `checkin/{userID}/{date}.jpg`、`report/{userID}/{uuid}` 组织，设生命周期策略定期归档。
- **消息推送**：审批/催办调 OpenIM 的 `/msg/send_msg` 发系统通知（用管理员 token，之前已验证可行）。

## 八、风险与待决事项

1. **HTTPS 是硬前提**：拍照和定位在非 HTTPS 下不可用，正式上线必须配证书，否则 F1 直接废掉。
2. **手机端适配**：现有 uni-app 工程可作为打卡入口载体，但要新做打卡/报告页面；PC 端 Web 做管理后台。
3. **GPS 围栏误差**：室内定位漂移，建议一期围栏放宽或做成可关闭，避免员工误判。
4. **管理端无源码**：现有 11002 管理前端是闭源产物，所有 OA 管理界面要新做，不能改它。这是工作量的大头，需提前评估。
5. **多分公司的执行风险**：隔离靠代码纪律，一旦某处漏了 `company_id` 条件就会串数据，是不可逆的信息泄露。必须靠"DAO 层强制注入 + 接口层校验 + 上线前专项渗透测试"三道防线兜底。
6. **建号流程要改**：现在员工由管理员在管理端创建，多公司后建号时必须指定 `company_id`，否则新员工无归属。这一步要和 OA 的建号接口一起做，不能后补。
7. **待你确认**：① 公司是单部门还是多层级？② 打卡是否强制 GPS 围栏？③ 报告点评人是直属上级固定，还是需要灵活指定？④ 是否需要和法定节假日同步？⑤ 目前有几家分公司、未来预计几家？⑥ 总部是否需要跨公司汇总看板？
