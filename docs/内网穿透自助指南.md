# 新搏 IM — 内网穿透自助指南

> 目的：不用公网 IP、不用开放防火墙入站端口，让团队从外网访问本机服务。
> 适用环境：Windows + Docker Compose + Git Bash。

---

## 一、先理解原理（30 秒）

传统访问是「外网直接连进来」，需要公网 IP 和开放端口。内网穿透反过来：

1. 你机器上的隧道客户端**主动向外连接**服务商的边缘节点；
2. 团队访问服务商给的公网地址；
3. 流量沿这条已建立的隧道**反向流回**你的机器，再转给本机服务。

因为连接是从内往外发的，所以**不需要公网 IP，也不需要开放入站端口**（出站一般默认放行）。这就是它能穿透公司/家庭路由器的原因。

隧道只转发 **HTTP / HTTPS / WebSocket**。WebRTC 的音视频走 **UDP**，穿不过普通 HTTP 隧道——所以语音视频的界面和信令能演示，但听不到声音、看不到画面。要真实通话必须另有公网 IP + 开放 UDP 7882，或部署 TURN。

---

## 二、方案对比：选哪个

| 方案 | 地址 | 成本 | 适合场景 | 难度 |
|---|---|---|---|---|
| **A. Cloudflare 快速隧道** | 随机 `xxx.trycloudflare.com`，重启就变，不给账号 | 免费 | 临时演示、给团队看一眼 | ★☆☆ |
| **B. Cloudflare 固定域名隧道** | 自己的域名，如 `im.company.com` | 免费（需已有域名托管在 Cloudflare） | 长期给团队用、要稳定地址 | ★★☆ |
| **C. frp / 自有服务器** | 自己服务器 IP + 端口 | 需一台有公网 IP 的服务器 | 完全自控、要传 UDP/自定义协议 | ★★★ |

**建议**：演示用 A，长期用 B，只有要真实公网通话才上 C。

## 三、方案 A：快速隧道（当前项目已配好）

### 1. 前提：目标服务必须是容器，且在同一 Docker 网络

这台机器的 Windows 防火墙会拦掉「容器 → 宿主机端口」，所以隧道**不能指向 5173 / 11001 这类宿主机端口**。必须指向容器名。项目里专门构建了带全部改动的源码版前端容器：

```bash
cd /d/work/openim/openim-docker-latest
docker ps --filter name=openim-tunnel-web --format "{{.Names}} {{.Status}}"
```

如果容器不在，先构建并启动（前端改动后需要重做这一步）：

```bash
cd src/openim-electron-demo
npx vite build --config vite.web.config.ts \
  --outDir "D:/work/openim/openim-docker-latest/release/tunnel-web" --emptyOutDir
cd ../..

docker rm -f openim-tunnel-web >/dev/null 2>&1 || true
docker run -d --name openim-tunnel-web --network openim-docker-latest_openim \
  -v "$(pwd -W)/release/tunnel-web:/usr/share/nginx/html:ro" \
  -v "$(pwd -W)/release/tunnel-web/nginx.conf:/etc/nginx/conf.d/default.conf:ro" \
  nginx:alpine
```

> 注意：构建会清空 `release/tunnel-web`，`nginx.conf` 会被一起删掉，构建后必须重新写回去。完整配置见本文末尾「附录：nginx.conf」。

### 2. 启动隧道

```bash
cd /d/work/openim/openim-docker-latest

# 启动（地址会打印在最后一行）
TUNNEL_TARGET=http://openim-tunnel-web:80 bash scripts/tunnel.sh start

# 只看当前地址
bash scripts/tunnel.sh url

# 停止
bash scripts/tunnel.sh stop
```

脚本本质是这一行 Docker 命令，理解后可以直接手写：

```bash
docker run --rm -d --name openim-tunnel \
  --network openim-docker-latest_openim \
  cloudflare/cloudflared:latest \
  tunnel --no-autoupdate --url http://openim-tunnel-web:80
```

地址从日志里取：`docker logs openim-tunnel | grep -o 'https://[a-z0-9-]*\.trycloudflare\.com' | head -1`

### 3. 验证

```bash
URL="https://你的地址.trycloudflare.com"
curl -s --noproxy '*' -o /dev/null -w "首页 %{http_code}\n" --max-time 25 "$URL/"
curl -s --noproxy '*' -X POST --max-time 25 -H "Content-Type: application/json" \
  -d '{}' "$URL/chat/account/login" | head -c 150
```

首页应返回 200；接口应返回业务错误码（说明请求已经转发到后端，不是 404/502）。

## 四、方案 B：固定域名隧道（长期给团队用）

### 1. 准备

- 一个域名，把 DNS 托管到 Cloudflare（免费）；
- 注册 Cloudflare 账号，进入 **Zero Trust → Networks → Tunnels**。

### 2. 创建隧道

1. 点 **Create a tunnel** → 类型选 **Cloudflared** → 起个名字；
2. 复制页面给出的 **Token**（形如一长串 base64）；
3. 本机启动（注意：**不要**带 `--url`，路由在面板里配）：

```bash
docker rm -f openim-tunnel >/dev/null 2>&1 || true
docker run --rm -d --name openim-tunnel \
  --network openim-docker-latest_openim \
  cloudflare/cloudflared:latest \
  tunnel --no-autoupdate run --token "粘贴你的TOKEN"
```

4. 面板里隧道状态变成 **HEALTHY** 即连上了。

### 3. 配置公网主机名

在隧道的 **Public Hostname** 里点 **Add a public hostname**：

| 字段 | 填什么 |
|---|---|
| Subdomain | `im`（或任意） |
| Domain | 选你的域名 |
| Service Type | `HTTP` |
| URL | `openim-tunnel-web:80`（**容器名**，不是 127.0.0.1，也不是宿主机端口） |

保存后等几十秒 DNS 生效，浏览器打开 `https://im.你的域名` 即可。

### 4. 加固（正式对外必做）

- 在 Cloudflare **Access** 里给这个域名加邮件验证码/企业 SSO，避免任何人拿到地址就能进；
- 关闭开放注册、换掉默认密钥（管理员 `chatAdmin/chatAdmin`、`secret=<CHANGE_ME_SECRET>` 等）；
- 把隧道容器加进 `docker-compose.yaml` 用 `restart: unless-stopped` 托管，避免重启后失联。

## 五、方案 C：自有服务器 + frp（要传 UDP 时用）

前提：有一台公网 IP 服务器（云主机即可）。

**服务器（frps）**，`frps.toml`：

```toml
bindPort = 7000
auth.token = "换成随机强密码"
```

```bash
docker run -d --name frps --network host \
  -v /path/frps.toml:/etc/frp/frps.toml \
  snowdreamtech/frps
```

**本机（frpc）**，`frpc.toml`：

```toml
serverAddr = "服务器公网IP"
serverPort = 7000
auth.token = "与服务器一致"

[[proxies]]
name = "xinbo-web"
type = "tcp"
localIP = "openim-tunnel-web"
localPort = 80
remotePort = 8080

[[proxies]]
name = "livekit-udp"
type = "udp"
localIP = "livekit"
localPort = 7882
remotePort = 7882
```

```bash
docker run -d --name frpc \
  --network openim-docker-latest_openim \
  -v "$(pwd -W)/frpc.toml:/etc/frp/frpc.toml" \
  snowdreamtech/frpc
```

访问 `http://服务器IP:8080`。frp 支持 UDP 代理，这是它比 Cloudflare 隧道强的地方——LiveKit 的 7882/udp 可以透出去，配合 TURN 就有机会实现公网真实通话。同时务必在云服务器安全组放行 7000/8080/7882。

## 六、这套环境最容易踩的 4 个坑

1. **隧道指向 127.0.0.1 无效**。隧道跑在容器里，它眼里的 127.0.0.1 是自己。必须写容器名（如 `openim-tunnel-web:80`）。
2. **容器连不上宿主机端口**。Windows 防火墙拦了 Docker 网桥到宿主机的入站，所以 `host.docker.internal:5173` 从隧道容器里访问不通。解决办法是把前端也做进容器（方案 A 第 1 步）。
3. **前端接口地址写死 127.0.0.1**。团队浏览器会去连他们自己的电脑。必须用同源相对地址 + 反代。项目里已改：`src/layout/useGlobalEvents.tsx`（SDK 地址按 `location.host` 动态生成）、`src/api/imApi.ts`（LiveKit 地址改同源 `/livekit`）、`vite.web.config.ts` 和 `release/tunnel-web/nginx.conf`（反代规则）。
4. **音频视频过不去**。HTTP 隧道只传信令。要真实通话，用方案 C 的 UDP 代理，或部署 TURN 服务器并让前端 ICE 走 TURN。

## 七、日常运维速查

```bash
cd /d/work/openim/openim-docker-latest

bash scripts/tunnel.sh start          # 启动（临时隧道）
bash scripts/tunnel.sh url            # 查看地址
bash scripts/tunnel.sh stop           # 停止，地址随即失效
docker logs openim-tunnel --tail 30    # 排查连不上
docker ps --filter name=openim-tunnel # 看容器状态

# 变更前端后重新构建隧道用产物
cd src/openim-electron-demo
npx vite build --config vite.web.config.ts \
  --outDir "D:/work/openim/openim-docker-latest/release/tunnel-web" --emptyOutDir
docker restart openim-tunnel-web
```

> 安全提醒：临时隧道地址任何人拿到都能访问，演示完请 `stop`。固定域名方案建议开 Cloudflare Access。

## 附录：nginx.conf（构建后写到 `release/tunnel-web/nginx.conf`）

```nginx
server {
    listen 80;
    server_name _;
    root /usr/share/nginx/html;
    include /etc/nginx/mime.types;
    default_type application/octet-stream;

    client_max_body_size 100m;
    gzip on;
    gzip_min_length 1k;
    gzip_types text/plain text/css text/javascript application/json application/javascript application/xml application/wasm;

    location / {
        add_header Cache-Control "no-cache";
        try_files $uri /index.html;
    }
    location ^~ /api/ {
        proxy_pass http://openim-server:10002/;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_read_timeout 120s;
    }
    location ^~ /chat/ {
        proxy_pass http://openim-chat:10008/;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_read_timeout 120s;
    }
    location ^~ /complete_admin/ {
        proxy_pass http://openim-chat:10009/;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_read_timeout 120s;
    }
    location ^~ /msg_gateway {
        proxy_pass http://openim-server:10001;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host $host;
        proxy_read_timeout 3600s;
        proxy_send_timeout 3600s;
    }
    location ^~ /oss/ {
        proxy_pass http://minio:9000/;
        proxy_http_version 1.1;
        proxy_set_header Host $http_host;
        client_max_body_size 100m;
    }
    location ^~ /livekit {
        proxy_pass http://livekit:7880;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host $host;
        proxy_read_timeout 3600s;
        proxy_send_timeout 3600s;
    }
}
```
