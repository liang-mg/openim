## 开工前全局性检查（用户明确要求 · 2026-11-19）

> 用户原话："在开发的时候要考虑全局性，比如前面的打卡，肯定要有一个记录表，组长可以看到你的出勤记录等等。下次根据这个要求来。"
>
> **每加一个功能，先按下面 8 条做设计，答不全就不要直接写页面/接口。** 这是开工前置条件，不是收尾检查。

| # | 开工前必须回答 | 为什么 |
|---|---|---|
| 1 | **数据落在哪张表？字段够不够支撑统计、导出、审批、审计？** | 打卡最早只存了照片和坐标，后来为地址、距离、围栏判定、照片 `file_id` 多次改表。表结构先定，页面后做。 |
| 2 | **记录表是不是从第一天就有？** 任何"提交 / 打卡 / 申请"动作，先建**不可变记录**（谁、何时、状态、附件 ID），再做录入 UI | 没有记录表就没有报表、没有追溯；用户点名"打卡肯定要有一个记录表，组长能看到出勤记录"。 |
| 3 | **四个视角都列出来了吗**：本人 / 组长 / 领导 / HR-管理员，各自看什么、改什么 | 打卡最初只有本人视角，组长看不到组员，后来才补 3.2。权限统一走 `visibleUserIDs`，不要在新接口里另写角色 `if`。 |
| 4 | **上下游谁会消费这份数据**：工作台待办、日报、审批中心、IM 推送、催交、导出 | 提前留好 `status` / `reviewer_id` / `reviewed_at` 等字段，否则接入时又得改表。 |
| 5 | **统计口径是不是只有一份实现？** 页面、报表、CSV 必须来自同一函数 | 曾出现同一份数据团队表显示迟到 1、报表显示迟到 0，这种表没人会信。 |
| 6 | **状态机和生命周期**：草稿→提交→审核→归档，谁能改、何时锁定；停用/离职后历史怎么处理 | H9（组长日报无人审）就是漏了状态流转，只能按关系判审阅人。 |
| 7 | **边界情况**：请假/出差、补卡、跨天夜班、未来日期、今天未下班、停用成员、空月份 | 缺卡被算成旷工、月中看全组出勤率往下掉，都源于没提前定义边界。 |
| 8 | **测试与文档同步**：权限矩阵用例 + UI 用例 + 设计文档一起交付 | 只改代码不补回归，下次改动就会悄悄打破它。 |

**交付前再确认一次**：上面 8 条的回答已经写进对应设计文档，接口、页面、回归脚本、文档四者一致。

### 批次 4 设计明细（P1-2 请假 + P1-3 补卡 · 开工前按 8 条清单评审）

| # | 清单项 | 本次的答案 |
|---|---|---|
| 1 | 数据落在哪张表 | 新建 `oa_leave`（不可变申请记录）+ `oa_makeup`（不可变申请记录）；`oa_checkin` 加 `source` / `makeup_id` 两字段标明记录来源，不动打卡唯一索引 |
| 2 | 记录表第一天就有 | 是。两张表从提交起就落库，带 `status / approver_id / approver_name / approved_at / comment`，审批前后全程留痕；审批不删记录、只改状态 |
| 3 | 四视角 | 员工看/撤自己的申请；组长批**直属下属**（`manager_id` 指向自己）；领导看整条汇报链；HR/管理员全公司。复用 `visibleUserIDs`，新接口里不写任何按角色的 `if` |
| 4 | 上下游消费 | 工作台待办数（真实 pending 数）；P2-2 审批中心预留 `kind=leave/makeup`；P2-3 IM 推送预留 `pending_approvals`；日报不消费；考勤统计消费 approved 记录 |
| 5 | 统计口径唯一 | 只在 `monthStatOf` 增加 `leaveDays` 入参：请假日不算缺卡、不计入应出勤分母；补卡通过后写入 `oa_checkin`，自然计入出勤。团队表、报表、CSV 都走这一个函数，删掉 `leave_not_integrated` 警告 |
| 6 | 状态机 | `pending → approved / rejected`，pending 可 `cancelled`；审批后锁定不可改；审批人=发起人的 `manager_id`，无上级时领导/HR 可批；不允许自批自 |
| 7 | 边界情况 | 请假只算工作日（周末不计天数，跨月按天拆到各自月份）；补卡只能补**过去 7 天**、每月上限 3 次（环境变量可配）、同一天同一类型已有卡则拒绝、不能补未来；停用成员不进审批链；补卡通过用 upsert 防重复 |
| 8 | 测试与文档 | 新增 `scripts/oa_leave_makeup_check.js`（权限矩阵 + 状态机 + 统计合并 + CSV），既有 5 个回归脚本全跑；设计写进 `docs/打卡功能-详细设计.md` 第十一节 |

**为什么请假不写 `oa_checkin`**：请假日不是"打了卡"，把它塞进打卡表会污染记录、破坏"打卡=真实现场"的原则。
请假只影响统计口径（不算缺卡、不算应出勤），在月历上显示"请假"状态即可。补卡则相反——它补的是**一次真实上班/下班事实**，
通过后必须生成 `source=makeup` 的打卡记录，否则出勤天数对不上。

## 三、依赖关系（照这个顺序做不会返工）

```
P0-1 文件服务 ──┬→ P0-2 打卡照片
                └→ P0-3 生产发布（附件能下载之后再发）

P1-1 规则（全局可配）──→ 3.2 团队出勤只读（按 manager_id 链）──→ P1-3 补卡（次数上限）
P1-2 请假 ──────┐
P1-3 补卡 ──────┼→ P1-4 汇总导出（请假/补卡口径合并）──→ P1-5 异常 ──→ P1-6 待办接入
                │
                └→ P2-2 审批中心 ──→ P2-3 IM 推送 ──→ P2-4 催交

P2-1 部门树 ──（顺延）→ 团队视图增加「按部门」维度，不改已有汇报链口径
```

**一句话顺序**：先补文件服务和发布（P0）→ 规则 + 团队出勤只读（3.1/3.2，组长立刻能用）→ 请假补卡 → 汇总导出与异常 → 审批中心和消息 → 看板审计。
部门树（P2-1）顺延到团队视图之后：出勤的团队范围先按 `manager_id` 汇报链算，不依赖部门字段。

## 四、需要你拍板的 9 件事

| # | 问题 | 我的建议（默认值） |
